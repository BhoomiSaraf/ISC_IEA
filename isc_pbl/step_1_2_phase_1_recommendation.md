### Q3: What can be reused?
Nearly **$90\%$ of the existing codebase can and should be reused directly**:
1. **The Cryptographic Envelope (`isc_cipher/container.py`):** The 36-byte ISCI header with versioning, profile tags, image dimension fields, and 128-bit nonce layout is robust and standards-compliant.
2. **The Key Schedule (`isc_cipher/kdf.py`):** The HKDF-SHA256 extract-and-expand engine with domain-separated context strings (`b"ISC-IMG/v1"`) and per-lane labeling enforces strict cryptographic separation.
3. **The State Mapping (`isc_cipher/state_map.py`):** The exact $2^{22}$-to-1 mapping from 16-byte seeds to the $2^{106}$-point Float64 grid in $[-1, 1]^2$ is mathematically proven and verified.
4. **The Ported Arithmetic Engine (`isc_cipher/fdlibm_ref.py`, `fdlibm_np.py`):** The Netlib fdlibm 5.3 port completely eliminates cross-platform floating-point divergence, ensuring identical ciphertexts across Windows, Linux, and macOS.
5. **The Sampling & Shuffling Primitives (`isc_cipher/sampling.py`):** Unbiased Lemire rejection sampling and Fisher–Yates permutations eliminate modular bias and sort-based side channels.
6. **The Non-linear Diffusion Engine (`isc_cipher/diffusion.py`):** Forward and backward chained modular addition with a keyed S-box provides fast avalanche, while algebraic invertibility allows vectorized, parallel decryption.
7. **The Integrity Layer (`isc_cipher/cipher.py`):** Encrypt-then-MAC with HMAC-SHA256 guarantees ciphertext integrity and strictly blocks unauthenticated plaintext release.
8. **The Evaluation Harness (`isc_eval/`):** The comparative harness implementing V-FULL, V-LINEAR, V-STREAM, V-PERM, V-CHACHA, and standard AEADs (AES-256-GCM, ChaCha20-Poly1305, AES-256-GCM-SIV) is completely operational.

### Q4: What must be corrected?
1. **Quantisation Inconsistency:**  
   The cipher extracts **bits 8–15 of the Float64 mantissa**, whereas Step 1.1 characterized the **$k = 14$ Fixed-Point Scaled-Floor-Modulo Transformation** ($B_n = \lfloor |x_n| \times 10^{14} \rfloor \bmod 256$). This discrepancy must be formally reconciled.
2. **Repository Fragmentation:**  
   The cipher codebase currently resides outside the active workspace (`sine_chebyshev_ikeda_analysis` vs. `ISC_PBL`). It must be unified cleanly into `ISC_PBL` without disturbing the frozen Step 1.1 characterization scripts.
3. **Permutation Generation Throughput:**  
   Generating large Fisher–Yates permutations ($N \ge 256 \times 256 = 65,536$) via scalar Python loops introduces latency. An optimized vector draw or batched Lemire prefetch will improve encryption speed without altering the mathematical definition.

### Q5: What is missing?
1. **Rigorous NIST STS Evaluation on the 256-Lane Generator:**  
   While Step 1.1 validated $k = 14$ on single long orbits, the 256-lane interleaved keystream generated by `generator.py` (which interleaves 64 lanes per stream) has only preliminary diagnostic runs in `results/encryption_experiments/A12_...`. A full multi-sequence NIST SP 800-22 evaluation of the cipher's actual keystreams (`fwd`, `bwd`, `perm`, `sbox`) is required.
2. **Full-Scale Experimental Benchmarks:**  
   The Gate A attack suite and comparative benchmarks against AES-256-GCM and ChaCha20-Poly1305 exist in script form, but final publication-grade runs across standard image datasets (Lena, Baboon, Peppers, Cameraman, USC-SIPI) must be executed and tabulated.
3. **Formal Plaintext Sensitivity (NPCR/UACI) Reporting Protocol:**  
   Under fresh random nonces, NPCR and UACI are trivially $\approx 99.61\%$ and $\approx 33.46\%$ (driven by nonce divergence). The evaluation must rigorously measure NPCR/UACI under **fixed-nonce differential plaintexts** to test the avalanche capability of the diffusion stage itself.

### Q6: Should we continue the existing architecture or design a new one?
**DECISION: CONTINUE AND RECONCILE THE EXISTING ARCHITECTURE.**  
Designing a new cipher from scratch would discard a verified, AEAD-compliant, bit-exact cryptographic system with 175 passing unit tests and C-oracle reproducibility. The existing architecture is exceptionally well-engineered and directly addresses the known vulnerabilities of chaotic ciphers (separability, linearity, key-only keystreams, cross-platform divergence).
